## 一、事实来源（按可信度排序）

1. **旧站线上渲染的 HTML**（一手）。取法：
   `curl -sS -A "Mozilla/5.0 Chrome/131.0" https://metalpartition.com/<path>`
   注意：旧站的 Shopify page `body_html` 基本是空的（0–45 字符），内容全在 LiveCanvas 模板里，
   **所以导出的 pages.json 不能当内容源**，只有渲染后的 HTML 能。
2. **`data/shopify-public/pages-content.md`**（266 KB，此前抓的旧站正文提取）。
   按 `# PAGE: <handle>` 分段，含 contact / faqs / 各 family 页 / 各 panels 页 / about /
   project-gallery / home 等。是最快的对照入口，但它可能比现在线上旧站旧，**冲突时以线上 HTML 为准**。
3. **`tools/audit/block_parity.py`**：把你负责的页面配对比一次，拿到「旧站有、新站没有」的
   逐条清单。用法：

   ```
   python3 tools/audit/block_parity.py --pair /pages/faqs /faqs/ --verbose
   ```

   它已经能区分「同一段话的标点差异」（会匹配）与「换了数字的另一段话」（不会匹配）。

## 二、必须忽略的噪声（不是缺口，别补）

`block_parity` 会把这些也报成 missing，它们**不是内容**：

| 报出来的样子 | 为什么忽略 |
|---|---|
| `Choosing a selection results in a full page refresh.` | Shopify 主题的屏幕阅读器助手文本，随 Shopify 平台存在 |
| `Opens in a new window.` | 同上 |
| `Skip to content` | 旧站有、新站确实没有 —— 这是真正的缺口，但由**另一条任务**统一修页头骨架，你不要动 |
| 旧站询盘表单的微文案（`Get in Touch` / `Or leave a message` / `Message (optional)` / `Message Sent`） | 新站的表单文案是**重写过的、经过裁定的**（spec 07/19），两边措辞不同是设计，不是缺失 |
| `Metal customization experts` / `Catalog, CAD, data sheet, and spec formats` 这类 metafield tab 标题 | Shopify metafield 的分组标签，新站用别的信息架构承载 |
| `<title>` 文本 | head 里的标题，已由 SEO 面单独验证（零缺失零重复） |

判断标准：**这句话是写给访客看的商业内容，还是平台/主题/后台机制自带的文本？**
只有前者才是缺口。

## 三、明确不许「补回来」的东西

上一轮已经**因为我方拿不出证据而删除**的自家测试数字，不许因为「旧站有」就搬回来：

- `4,000+ hr ASTM B117`、`4,000hr+ Salt Spray Tested`
- `25+ Year Finish Life`、`25+ years weathering`
- `500–1000 hrs`、`10–20 year warranty`、`10–15 years`
- 任何「我方实测寿命 / 盐雾小时数 / 质保年限」

理由：这些是我方对自己产品做的**事实性断言**，不是旧站的设计内容；旧站写它们只是旧站写了。
`ASTM B117` 作为**标准代号**可以出现（它不是我方的实测值）。

**遇到这类内容：不要恢复，写进报告的「不予恢复」清单，附原文与位置。**

同理，价格区间（`40–160 USD/m²`、`$40–$80/sqm`、`30–60%` 加价）**先不要动**：
它们是我方对外报价口径，属商业裁定，写进报告交业主定，不要在没人拍板时搬上去。

### 3.1 补充裁定（主代理，2026-10-29 本轮）

## 四、该补的「实质内容」长什么样

按旧站逐块比对，逐条判断。典型该补的：

- 整段说明文案、章节标题与副标题、章节引言；
- FAQ 的问与答（问句与答句都是内容）；
- 规格表 / 对比表的行与列（表头也是内容）；
- 流程步骤的编号、标题、说明；
- 应用场景描述（如 `Facade Screens` / `Balcony Privacy Screens` 每一块的定义与适用条件）；
- 案例研究的字段（项目名、地点、材料、厚度、工艺、面积）；
- 统计条（`Countries served 15+` 这类，若旧站有且我方没有）；
- 图片 alt 里承载的说明（若旧站 alt 是描述性长句，新站空 alt 要补）。

## 五、实现纪律（照 AGENTS.md，违反会被守卫测试打红）

1. **呈现层优先级**：① LiveCanvas 原生 tag → ② WooCommerce 原生机制 → ③ WindPress 类与 tokens
   → ④ 自定义代码（最后手段）。
2. **PHP 只做数据装配**，零内联样式、零设计决策。客户可见文案一律进 LiveCanvas 模板，
   **不许写进 PHP 字符串**。
3. **不许新建 CSS 文件**、不许建第二条 Tailwind 构建。缺类就加到对应 WindPress 卷
   （`plugins/md-site/content/windpress/*.css`）里，用既有 tokens。
4. **不许改设计体系**：字号阶梯、间距节奏、颜色 tokens 一律沿用现状。你补的是内容，
   不是重新设计。业主对「样式不好看」的意见由别的任务处理，你不要顺手改视觉。
5. **不许外包图片**：任何图片只能引用媒体库里已存在的文件（`/wp-content/uploads/...`），
   **不许出现外部图片 URL、不许第三方图床、不许 hotlink**。缺图就写进报告，由搜索任务补。
6. **不许减少内容**：不能为了版面好看删旧站已有的块。业主明令：「不能以通过减少图案的方式去优化」。
7. **只改分配给你的文件**。不要动 `partials/header.html`、`partials/footer.html`、
   `partials/md-inquiry-cta.html`、`assets/js/md-chrome.js` —— 这些在别的任务手里，
   同时改会互相覆盖。
8. 不要部署。不要截图（浏览器是单窗口共享资源，由单独一条任务串行跑）。
9. 改完必须跑：`just check`，以及 `just php-test` 里受影响的那一包。全绿才算交付。
